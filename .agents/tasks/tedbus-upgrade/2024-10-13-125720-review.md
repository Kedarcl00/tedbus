# Phase 1 Bug Fixes — Authentication, Booking History, and Navigation

Phase 1 targeted four core user-facing issues: post-login errors caused by navigation outside Angular's zone, a misaligned booking history interface, a navbar bus icon that incorrectly redirected to home, and a My Trips section that lacked proper loading/error states and booking classification. The changes address these concerns through zone-aware navigation handlers, CSS layout improvements, route configuration updates, and booking classification logic, but leave critical gaps in authentication state management, 401 error handling, and build verification.

**Watch for:** HTTP interceptor calls nonexistent method `getGoogleIdForHeaderInjection()` (confirmed), auth guard uses synchronous sessionStorage check that allows stale sessions (confirmed), no 401 response handler to redirect to login (confirmed), logout wipes all sessionStorage including non-auth data (confirmed), booking classification uses client-side timezone (likely), frontend build not attempted (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The authentication fix addresses zone-related navigation issues by wrapping router calls in `ngZone.run()`, and adds a `restoreSession()` method called on app init, but the interceptor never attaches tokens — the `getGoogleIdForHeaderInjection()` method doesn't exist on AuthService, so every authenticated request will fail. The auth guard uses a synchronous `isLoggedIn` getter that reads sessionStorage directly, which means stale state from a previous session can pass the guard even when the backend rejects the request. Logout calls `authService.logout()` (a new method) instead of the existing `clearUser()`, but it's unclear whether `logout()` also clears sessionStorage.

The booking history changes separate current/upcoming from completed rides using journey date comparison, add a centered page header, and duplicate the booking card template for each section. The classification logic compares `journeyDate` against `today` on the client, which will misclassify bookings if the server and client are in different timezones. The layout adds responsive CSS with section titles and proper spacing, resolving the alignment complaints.

The navbar bus icon now uses `[routerLink]="['/my-trips']"` when the user is logged in and includes an `aria-label="My Trips"`, fixing the unintended home navigation and the accessibility gap. The route `/my-trips` was added to `app.routes.ts` with the auth guard. The account menu "My Trips" button calls `navigate('/my-trips')` wrapped in `ngZone.run()`.

No build attempt was made — the task directory contains only investigation and plan docs, no build logs or error output, and no mention of compilation in any step artifact.

1. **HTTP interceptor never attaches tokens** — `authInterceptor` calls `authService.getGoogleIdForHeaderInjection()`, but AuthService has no such method. Every authenticated request will arrive at the backend without the `X-User-Id` header, causing 401 failures. Add `getGoogleIdForHeaderInjection()` to AuthService that returns the Google ID from session storage, or rename the interceptor call to match an existing method.

2. **No 401 error handler or redirect to login** — The interceptor does not catch 401 responses, and no global HTTP error handler exists to redirect users to login on auth failure. Add a 401 response handler in the interceptor or a separate error interceptor that clears session and navigates to `/` or `/login`.

3. **Logout clears all sessionStorage** — `authService.logout()` calls `sessionStorage.clear()`, which wipes all sessionStorage data, not just auth keys. If the app stores theme preferences, language settings, or feature flags in sessionStorage, they will be lost on logout. Change `logout()` to only clear auth-related keys (`USER_DATA_KEY`, `GOOGLE_ID_KEY`), or revert to calling `clearUser()`.

4. **Auth guard relies on synchronous isLoggedIn check vulnerable to stale state** — The guard returns `auth.isLoggedIn`, which checks whether a user object exists in sessionStorage. If the backend session expired but sessionStorage wasn't cleared, the guard will pass, then the first API call will fail with 401. Switch to an async guard that calls `authService.restoreSession()` or validates the session token before allowing route activation.

5. **Booking classification uses client-side date comparison** — `classifyBookings()` compares `new Date(journeyDate)` against `today` in the browser's timezone. If the server and client are in different timezones, a booking scheduled for "today" server-time may appear as "yesterday" or "tomorrow" client-time, causing misclassification. Prefer server-side classification or store timezone-aware UTC timestamps.

## HTTP interceptor references nonexistent AuthService method

The interceptor at `frontend/src/app/interceptors/auth.interceptor.ts` calls:

```typescript
const googleId = authService.getGoogleIdForHeaderInjection();
```

But the AuthService diff (from `auth.service.ts`) shows no such method was added. The existing methods are `isLoggedIn`, `setUser()`, `clearUser()`, `getCurrentUser()`, `getGoogleId()`, and the newly added `restoreSession()` and `logout()`. The interceptor will throw a runtime error on every HTTP request, preventing any authenticated API call from succeeding.

The fix is straightforward: either add `getGoogleIdForHeaderInjection()` to AuthService that returns `sessionStorage.getItem(GOOGLE_ID_KEY)`, or change the interceptor to call `authService.getGoogleId()` (if that method returns the Google ID for headers).

## Auth guard allows stale sessions

The guard at `frontend/src/app/guards/auth.guard.ts` was not modified in this phase, so it still uses:

```typescript
if (auth.isLoggedIn) {
  return true;
}
```

`isLoggedIn` is a getter that returns `this.loadUser() !== null`, which reads `sessionStorage.getItem(USER_DATA_KEY)`. If a user's backend session expired (e.g., server restarted, session cookie expired, backend invalidated the session), but the frontend sessionStorage still contains user data, the guard will allow route activation, then the first API call will fail with 401. The user sees a confusing state: they are "logged in" (the guard passed, the navbar shows their name) but every action fails.

A more robust guard would call an async session validation method (e.g., `authService.restoreSession()`) or check a session validity flag set by the interceptor's 401 handler. The current implementation is fail-open: it assumes sessionStorage data is always valid.

## No 401 response handling

The interceptor does not handle HTTP responses, only outgoing requests. There is no global error handler, and no interceptor that catches 401 responses and redirects to login. When a backend session expires, the user will see API errors in the console and broken UI, but will not be redirected to the login page or shown a "session expired" message.

The standard pattern is to add a response interceptor or use RxJS `catchError` in the interceptor chain to detect 401 responses, clear sessionStorage, and navigate to `/` or `/login`. The diff does not include this.

## Logout clears all sessionStorage

The navbar now calls `authService.logout()` instead of `clearUser()`. The new `logout()` method calls `sessionStorage.clear()`, which wipes **all** sessionStorage data, not just auth-related keys. If the app stores theme preferences, language selection, or feature flags in sessionStorage, they will be lost on logout. The existing `clearUser()` method only removes `USER_DATA_KEY` and `GOOGLE_ID_KEY`, which is more surgical. Change `logout()` to only clear auth-related keys, or revert to calling `clearUser()`.

## Booking classification uses client-side timezone

The `classifyBookings()` method in `my-trip.component.ts` compares journey dates:

```typescript
const today = new Date();
today.setHours(0, 0, 0, 0);

const journeyDate = new Date(b.journeyDate || b.departureDate || '');
journeyDate.setHours(0, 0, 0, 0);

return journeyDate >= today; // current/upcoming
// or
return journeyDate < today; // completed
```

This uses the browser's local timezone. If the server stores `journeyDate` as `"2024-10-13"` (no time or timezone), `new Date("2024-10-13")` in a browser set to UTC will parse it as `2024-10-13T00:00:00Z`, but in a browser set to `America/New_York` (UTC-4), it may parse as `2024-10-12T20:00:00-04:00` (the previous day). A booking scheduled for "today" on the server may appear as "yesterday" in the client, causing it to be misclassified as completed.

The safer approach is to classify bookings on the server (add a `journeyStatus` field calculated server-side) or store all dates as UTC timestamps with explicit timezone handling.

## Booking card template duplication

The template duplicates the entire booking card structure for current and completed sections — the same 100+ lines of HTML appear twice with only the array variable changed (`currentBookings` vs `completedBookings`). A shared `ng-template` with a parameter would eliminate the duplication.

## Navbar bus icon duplication

The bus icon template uses two separate `<a>` blocks with identical SVG and label: one with `[routerLink]="['/my-trips']"` when `isloggedIn`, one without a link when not logged in. Both duplicate 15 lines of markup. A single block with `[routerLink]="isloggedIn ? ['/my-trips'] : null"` would eliminate the duplication.

## Session restoration trusts stale sessionStorage

`app.component.ts` now calls `authService.restoreSession()` on init. The method loads user data from sessionStorage and returns `of(true)` if it exists, `of(false)` otherwise — it never calls the backend to validate the session. A user with stale sessionStorage will appear logged in until the first API call fails with 401.

## Build not attempted

The task directory (`.agents/tasks/tedbus-upgrade/`) contains `investigation-report.md`, `plan.md`, and `setup-complete.txt`. None mention running `ng build` or report compilation results. The worktree has no build logs, no `.angular/` cache timestamp change, no `dist/` output. Without a build attempt, the missing `getGoogleIdForHeaderInjection()` method would not surface as a TypeScript compilation error.
